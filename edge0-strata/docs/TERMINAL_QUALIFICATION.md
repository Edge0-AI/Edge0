# Terminal qualification matrix

> **Historical record (11 October 2026).** This page was written while the Terminal was being built, before Strata 0.2.0. It is kept for the record and is not kept up to date: it describes six views, source-run commands and checks that had not yet been run on target hardware. For what the Terminal does now, see [TERMINAL.md](TERMINAL.md), [TERMINAL_LAUNCH.md](TERMINAL_LAUNCH.md) and [TERMINAL_QUICKSTART.md](TERMINAL_QUICKSTART.md).

This matrix separates checks already run in this source checkout from release gates that need the supplied UI/harness/TUI assets or a target host. A passed synthetic client test does not establish engine performance or platform support. Record exact commands, source commit, artifacts and environment for every final gate.

## Target-host run order

1. Install the exact reviewed build in a clean Windows or Linux environment; record installer/component hashes, versions, rights/notices and rollback result. Confirm the pure server starts with Desktop, harness and Textual absent. Install and remove the optional Monitor separately.
2. Create a saved four-card profile, run `profile show --effective`, `doctor --components --live`, `components verify --live`, `runtime start` and `runtime verify`. Save the effective argv, owned instance ID, configured and resolved device order, model identity and actual slot/group counts. A successful one-token verify is only a smoke check.
3. Use `status --json` and the Serving, Requests, Engine, Hardware and Logs views at 110, 80, 60 and 40 columns. Verify each displayed count against the v1 response and the [field matrix](TERMINAL_TELEMETRY_FIELDS.md). Record unavailable fields explicitly. For opt-in BSTAT/PSTAT samples, retain raw engine lines, sample windows/age and native-backend build identity. A reported layer range must not be labelled live GPU occupancy.
4. Run the same fixed serving workload with no monitor, default Monitor, 0.5-second Monitor and Monitor plus the coding client. Warm up, then retain at least three repeated trials per condition. Save `bench run` directories and `bench compare` results only when workload fingerprints and available environment match. Measure server and terminal CPU/RSS separately, HTTP calls/bytes/s, tokens/s, client TTFT, queue wait, cancellation latency and every slow or failed request. Declare pass budgets from the M0 baseline before looking at the trial deltas.
5. Run mixed parallel, overload, active/queued cancellation and partial-prompt cancellation suites with the monitor both attached and detached. Choose concurrency from reported effective slots and admission limit; the overload suite must exceed the limit. Exercise at least ten load/generate/cancel/unload cycles and verify no orphan workers, stale topology, leaked request content or changed engine state after monitor detach.
6. Restart the server during a 30-minute real Monitor soak, add two deliberate network interruptions, and check bounded memory/rows, one in-flight poll, reconnect, selection reset and clean detach. Repeat terminal key, resize, freeze, theme, color and ASCII glyph checks on each supported OS/terminal. Capture actual terminal screenshots separately from illustrative fixtures.

The synthetic `tools/monitor_soak.py` report is a useful client regression check before step 6. It runs a local fake telemetry server and cannot supply the real server CPU/RSS, inference performance, native GPU sample accuracy or operating-system qualification required above.
