## 2. Required final behavior

The Desktop UI and CLI must act on the **same installed profiles, runtime instances, component inventory and operation records**. The TUI is an attachable, read-only monitor for Server users. The coding CLI and Desktop chat must use the same harness session/approval service. The engine is not copied into each front end.

```text
Owner's UI controls           CLI operator commands          Monitor TUI
         |                             |                    read only
         +----------- typed local management API ------------+
                               |
              profile store + operation journal + inventory
                               |
             runtime worker / Python API / existing C++ engine
                               |
                    model pack + backend + telemetry

Desktop Chat -------- shared harness session/approval service -------- strata code
```

The source-run CLI and a trusted Desktop host can call the same typed runtime path through `strata_control.management`; see `docs/MANAGEMENT_PROTOCOL.md` for the one-shot local JSON contract. Desktop start must take the profile revision and source digest from `runtime.start.plan`; the bridge checks both before journaling and the owner host checks them again before engine launch. Reviewed Stop and Restart commands pin the owner and instance IDs shown by their plans, checked again inside the owner before drain. Restart also pins the candidate profile revision and source digest. The imported Node host now has an internal `native-runtime.mjs` child-process adapter and an opt-in `/api/native/runtime` route for one host-configured saved profile. Native mode shows Serving, Monitor, Models, Profile and Components. Serving presents owner status and reviewed Start/Stop/Restart/Verify; a 90-second single-use server-side plan pins the action. Verify also pins the reviewed owner and instance IDs, rechecked inside the owner before an optional one-token generation; loading an unloaded model is a separate explicit choice. Monitor reads bounded `/v1/telemetry` from the owned local instance, checks its instance ID and keeps the read-only key on the host. Components calls `components.inspect` through the same Python management bridge as the CLI, bounds fields before browser delivery and runs the host GPU probe only after a manual request. Models calls `models.installed`, `models.inspect` and `models.import.plan` through that bridge; the browser sees bounded report fields and never receives a claim of verified engine compatibility. Profile reads the saved profile and installed run configs, then uses a single-use server-side review; Python rechecks the old revision and source digest before saving, and the running instance remains unchanged until a separate reviewed restart. A changed source or edited config triggers an explicit source-change review in Serving before the owner drains the old instance. The route requires a loopback bind and local Host/Origin, and action POSTs need JSON plus a custom header. This is a local preview boundary, not audited Desktop authentication. With `STRATA_NATIVE_PROFILE` set, all prototype HTTP mutations and `/v1` inference are rejected, the prototype monitor sampler is not started, and `STRATA_REAL_ENGINE=1` is incompatible. Its separate browser profile store and remaining prototype views must be mapped or retired after parity checks. There is one lifecycle authority per runtime instance. Every operation has an instance/profile ID, owner, plan, progress events, result, cancellation policy and audit record. The UI and CLI are clients of that authority; neither builds a second installer or calls arbitrary shell strings from a browser request. A monitor credential grants `/v1/telemetry` only. An inference credential cannot install, calibrate or run commands. Partner hosts such as Unsloth own their registered Strata runtime lifecycle through the separate host adapter contract.

## 3. Easy-to-edit operational commands

### User experience

An owner should be able to choose a saved serving profile, edit its model/device/parallel/batch parameters, preview the effect, then run the same action from UI or CLI. Save profile revisions so a successful configuration can be restored. Surface the exact effective engine arguments, component versions and resolved paths in the preview with secrets redacted.

**Proposed public grammar (target, not all implemented):**

```text
strata profile list
strata profile create four-gpu --from-config CONFIG.json
strata profile show four-gpu --effective --output json
strata profile edit four-gpu
strata profile set four-gpu parallel=8 max_queue=32 queue_timeout=15 batch_telemetry=true
strata profile set four-gpu parallel=8 --plan
strata profile use-config four-gpu --from-config /absolute/path/next-model.json --plan
strata profile use-config four-gpu --from-config /absolute/path/next-model.json --if-revision PROFILE_REVISION
strata profile validate four-gpu
strata profile history four-gpu
strata profile rollback four-gpu --to REVISION
```

Opt-in `batch_telemetry=true` yields low-rate engine samples of processed verifier rows and active request slots per batch window, with a sample age; the default and older engines keep those values unavailable. This native path remains unbuilt and unqualified on CUDA, HIP and SYCL. Grouped-pipeline stage in-flight fractions now come from opt-in engine host spans; they include poll delay and are not GPU kernel occupancy. Client-observed TTFT, GPU kernel occupancy, non-grouped stage timing and a complete request lifecycle remain unavailable in the monitor and must stay labelled as such until instrumented.

The Overview shows prompt-reading progress only when a request reports both a read count and prompt length. It summarizes reading, decoding and idle slot phases only when the effective slot report is complete and unambiguous. Exact pipeline group occupancy additionally requires a valid group on every effective slot; a partial or ambiguous report shows unavailable instead of a numeric fraction. The normalizer and bounded client also leave occupied slots unavailable when the source slot list is truncated or ambiguous; the client derives the number from validated slots instead of trusting a conflicting field. A bounded output-throughput trend shows the range over the displayed polling samples; it resets on an instance change and disappears with stale or missing rates. At wide sizes, separate recent-poll trends show processed batch rows/window and pre-admission queue count; replica mode shows each child batch series separately, never a cross-replica average. These trends have bounded sample counts and visible min/max ranges, reset on an instance change, and disappear when their newest source value is missing, its batch sample is more than five seconds old, or the connection is stale. The Overview hides batch and host-span numbers from engine samples older than five seconds; detail views retain the last value with its age. They are display histories, not extra engine measurements. After any failed collection, the first healthy snapshot establishes a new rate baseline while activity sequence tracking remains intact; the next consecutive healthy sample can report aggregate throughput. It marks a reachable unloaded model `SLEEPING` and suppresses stale speed readings. On initial attach, disconnect, rejected credentials or incompatible telemetry, a dedicated connection panel replaces cached request and GPU values in all six views, including compact 40-column layouts. Disconnects retry automatically; credential and schema failures require manual refresh after correction. Automatic glyph selection uses Unicode block history graphs when the output encoding supports them and ASCII on limited streams. `--glyphs braille` offers denser cells on terminals with a supporting font; `--glyphs ascii` forces a plain fallback.

A portable `strata-monitor.pyz` can be built from `packaging/monitor_bundle.py`. It contains only the read-only client, renderer, one-screen dashboard, optional TUI module, shared status/monitor/logs grammar and Strata MIT notice; no engine or model files. `status`, `monitor --once` and `logs` work with standard-library Python, while interactive mode requires an explicit Textual install. The version-3 manifest checks SHA-256, bundle members, Python 3.10 minimum, telemetry schema 1 and the license notice; version-1 and version-2 source bundles remain verifiable for update/rollback. Eight focused bundle tests passed on the current Python 3.11 worktree; the version-3 artifact was built and verified with Python 3.10, and its standard-library connection command ran there without site packages. The earlier version-2 build passed the same tests on Python 3.10 and 3.11 on macOS. The manifest is unsigned. A local `install` command verifies the bundle, requires the candidate SHA-256 from its preview, copies it into a new directory and verifies the copy. A hash-pinned `update` retains one previous client; `rollback` exchanges the two verified copies, and `commit` removes the previous copy. `uninstall` requires the active SHA-256 from its preview and refuses a directory with unexpected files or an uncommitted previous copy. None of these commands installs Textual or changes the server. Treat this as a source-run transfer artifact; signed optional components and clean Windows/Linux install and update qualification remain release gates.

### Editable recipe format

The source-run CLI stores one versioned recipe file per operation under the owner-only profile directory. Its current schema uses `schema_version`, `profile`, `id`, `kind` and typed `params`. The three supported kinds are `runtime.restart` with `startup_wait_s`, `engine.calibrate.measure` with an absolute `report_dir`, and `components.verify` with optional boolean `live` (false by default). The calibration suite is still the fixed decode sweep. Recipes are not shell scripts and cannot embed arbitrary command text. The developer must connect UI forms and CLI edits to one validated schema and operation service. The example below is a **future target schema**, not a current Strata config file:

```json
{
  "schema_version": 1,
  "profile": "four-gpu",
  "model_ref": "installed-model-id",
  "devices": [0, 1, 2, 3],
  "parallel": 8,
  "batch_groups": "auto",
  "max_queue": 32,
  "queue_timeout": 15,
  "operations": {
    "restart": { "kind": "runtime.restart", "drain_timeout_s": 30 },
    "calibrate": { "kind": "engine.calibrate", "suite": "throughput-and-latency", "trials": 3 },
    "check": { "kind": "components.verify", "scope": ["engine", "backend", "model", "tokenizer", "api"] }
  }
}
```

Keep canonical model profiles, user overrides and temporary command flags separate. The effective preview shows which layer supplied each value; the active runtime records a snapshot of what actually launched. Changes to the file do not silently restart a running model. A profile and recipe have stable IDs and a schema version. Validate ranges, model/backend capabilities and incompatible sampling or batch modes before GPU allocation. Use argument arrays and typed values when invoking owned processes. Do not splice raw command text into a shell.

For expert developers who truly need a custom local tool, a separate **local-owner-only** `exec` recipe may accept an absolute executable path, an argv array, a fixed working directory and named environment references. It is opt-in, never served through inference or telemetry APIs, never constructed from model output, and displays the exact command and effects before execution. First-class restart, calibration, doctor and benchmark flows should use typed operations instead of this escape hatch.

### Operation semantics

| Operation | Preview / checks | Execution and result |
| --- | --- | --- |
| Restart or rerun model | Resolve installed model, backend binary, devices, pack/schema, context, requested slots/groups and effective args. Check port and available resources. | Stop new admissions, drain/cancel within deadline, start the owned instance from a saved profile revision, wait for generation readiness, and report actual slots/groups. On failed activation, restore the previous working profile/runtime selection where safe. Never kill unrelated GPU processes. |
| Calibrate engine | Show scope, expected duration, exact hardware/model key, parameters and benchmark suite. `--plan` performs no mutation or network access. | `--measure` obtains exclusive access or an explicitly drained instance, runs repeated trials and saves a signed or hash-bound report containing baseline, raw trials, candidate and hardware/model identity; it does not change the active config. `--apply-result` checks report freshness and identity, saves the prior config, applies the candidate, then verifies a smoke generation. On failure restore previous settings. Report latency and throughput rather than only fastest tok/s. |
| Doctor / component check | Read installed component manifests and inspect engine binary/version/protocol, backend and driver, selected GPUs, model shards and hashes, tokenizer/template, optional vision, TUI and harness compatibility. Label unverified checks. | Read-only report with stable issue codes, severity and repair suggestions. A separate explicit repair plan may download or replace artifacts; doctor never repairs by itself. |
| Benchmark | Resolve a named, versioned workload and output directory; show model/config/hardware identity. | Run only on explicit request, record JSON evidence and environment, include four-GPU mixed long/short prompts, cancels and overload, and compare with a pinned baseline. No benchmark runs when opening Monitor. |

The operator surfaces must show command state (`planned`, `waiting`, `running`, `cancelling`, `succeeded`, `failed`), timestamps, log location, resulting instance ID and whether any change applied. CLI `--output json`/`jsonl` must remain machine-clean. Secrets are referenced by owner-controlled storage, not embedded in recipes, shell histories, ready files or operation logs.

### Four-GPU serving visibility

A 4 x RTX 6000 operator should see one aggregate line and four card rows in the selected-device order, updated from measured telemetry. A missing or duplicate card sensor leaves that selected row visible with unavailable readings and no stale utilization graph instead of substituting another host GPU. Client device history is capped at the currently selected card indices. Keep **running requests**, **occupied decode/prefill slots**, **engine waiting**, **pre-admission queue**, **rejections and timeouts**, **batch groups**, **batch size/window**, **throughput**, **TTFT** and **per-card memory/utilization** as distinct fields. A missing backend signal is `unavailable`, not zero or a guessed mapping. Group membership must identify the engine’s actual slot groups; stage placement is a separate engine-reported mapping, and time-series views should reveal whether batching improves throughput while harming tail latency. Provide terminal widths around 110 and 80 columns plus a compact 60-column view; preserve a clean JSON snapshot for scripts. Validate all labels against the engine scheduler before using the TUI as a performance dashboard.

One acceptance scenario should run mixed short and long requests at a recorded parallel setting, increase arrival rate until queue admission is exercised, cancel an in-flight request, then drain and restart the model. Save synchronized CLI JSON, TUI capture, backend counters and benchmark output. The expected invariant is that aggregate and per-card counts reconcile with the scheduler and that no request disappears between admitted, waiting, active, cancelled, completed and rejected states. Record the exact RTX 6000 generation and memory size with the driver, topology and model; the card name alone is insufficient.
